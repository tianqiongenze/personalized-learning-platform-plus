## 背景

PLPP 四库(iam_db/tenant_db/course_db/teaching_db)当前全量在 CRDB v25.4.0(3 节点 `--insecure`)。用户要求 CRDB 与 TiDB 双数据存储层**可动态自由切换**, 且 TiDB 侧带 TiFlash 列存做 HTAP 分析加速。

**ESP 教训(必须吸收)**:

1. **ESP 曾全量 TiDB 后转 CRDB**(ADR-24): 转移动因是 mirror 拉不到 pingcap 镜像 + 单二进制运维简单 + esp-rw-java 已有 CRDB 路径。**代价是 HTAP 学情分析路径丢失且无替代方案记录**(ADS 铁律违规)。PLPP 的差异: PLPP 的 TiDB 集群**已在 infra ns 稳定运行**(v8.5.8, 8 天前部署, 与 CRDB 共存于同一集群的 infra namespace), 镜像问题已被"节点 daocloud mirror 拉取 → retag 私仓"路径解决 — ESP 当年的两个根因(mirror 403、运维复杂)在 PLPP 场景均不存在或已缓解。
2. **schema 兼容性**: TiDB `AUTO_RANDOM` ↔ CRDB `unique_rowid()`、`ON UPDATE CURRENT_TIMESTAMP` ↔ 应用层维护、UUID→CHAR(36)、BOOL→BIT(1) 等差异在 live 对拍中实测确认(见 §6)。
3. **切换必须显式 ADR 记录, 禁静默切换**(ESP ADR-24 回切条件第 5 条原文)。

**PLPP 与 ESP 场景差异(写明)**:

| 维度 | ESP | PLPP |
|---|---|---|
| TiDB 集群 | 3 逻辑 region 已下电(scale=0), ExternalName 残留 | infra ns 实际运行, v8.5.8 全组件 |
| 切换实现 | `ESP_RW_STORAGE_TYPE` + 服务内 SharedDataSourceConfig 双 bean 互斥 | `APP_STORAGE_TYPE` + platform-common `com.platform.common.storage` 共享包(服务零代码切换) |
| 数据规模 | 30 亿 learning_events | 四库表近空(<100 行), 双向迁移成本低 |
| HTAP | TiFlash 丢失后无补偿 | TiFlash 集群已在位, ADR-005 落地读路径 |

## 决策

**CRDB 保持默认数据面; TiDB 作为完整对等数据面在 platform-common 层落地, 运行时 env 切换。**

- **实现位置**: `platform-common/src/main/java/com/platform/common/storage/`(注册方式对齐既有 `com.platform.common.rw`):
  - `StorageProperties`(`app.storage.*`): `type=cockroachdb(默认)|tidb` + 两套独立连接组 `cockroachdb.url/driver/...`、`tidb.url/driver/...`(显式分离防"切 type 忘切 url")。
  - `StorageDataSourceAutoConfiguration`: `@ConditionalOnProperty` 互斥装配 CRDB 池(PG 驱动)或 TiDB 池(MySQL 驱动, `com.mysql:mysql-connector-j` pom optional); 默认 `app.storage.enabled=false` 不影响现有部署。
  - `META-INF/spring/...AutoConfiguration.imports` 注册。
- **动态切换语义**: k8s env `APP_STORAGE_TYPE` → Spring relaxed binding 映射 `app.storage.type`; 切到 TiDB 时**必须同步** `SPRING_DATASOURCE_URL=jdbc:mysql://tidb.infra:4000/<db>`、`SPRING_DATASOURCE_DRIVER_CLASS_NAME=com.mysql.cj.jdbc.Driver`、`HIBERNATE_DIALECT=org.hibernate.dialect.MySQLDialect`(各服务 application.yml 已留注释说明)。env 一改即切, 不改代码、不重打包。
- **与读写分离正交**: `app.storage.*` 选库, `app.rw.*` 库内路由; TiDB 模式下 rw 双池上游换为 tidb svc(CRDB follower-read 语义退化为 TiDB 副本读, 见回切条件)。
- **集群清单**: infra ns 的 TiDB 集群 live 清单已固化回写 `k8s/base/tidb.yaml`(DGO 铁律: pd×3/tikv×3/tidb×1/tiflash×1 + svc + cm + pvc, 镜像 pin `pingcap/*:v8.5.8-x86v1`)。

## 代价 / 技术债

1. **schema 双向漂移风险**: CRDB 与 TiDB 各自演进 migration(Flyway V1/V2), 无 schema 对拍门禁 — 双库并存期 schema 漂移靠人工, 长期需 CI 对拍(DEFERRED)。
2. **Hibernate 方言差异**: `CockroachDialect`(默认) vs `MySQLDialect` 需 env 同步切换; `ddl-auto=update` 在双库并存期不可用(以某库为准手工维护)。
3. **事务语义差异**: CRDB SERIALIZABLE vs TiDB 默认 REPEATABLE READ(SI); 依赖串行化防 lost update 的路径(OCC 铁律)切 TiDB 后需显式 `BEGIN pessimistic` 或版本列兜底 — PLPP 现有写路径以乐观幂等为主, 风险可控但需测试覆盖。
4. **insecure 模式**: CRDB `--insecure` 仅适合内网验证拓扑, 不可作为生产姿态(与 TiDB 无认证接入同属待收敛项)。

## 回切条件(双向)

**→ TiDB(主切)**: 四库 schema 在 TiDB 侧验证通过(live 已建同构表) + 服务 env 切换 smoke 通过 + TiFlash replica AVAILABLE(ADR-005)。切换操作 = 改 env + 滚动重启, 需新 ADR 记录动因。

**→ CRDB(回切)**: 出现以下任一即回 — ① TiDB 集群出现跨版本数据格式故障(RDB/WAL 不兼容, SVD 教训); ② tiflash 持续 CrashLoop 且业务无分析读需求; ③ TiDB 运维资源(镜像/节点)不可持续。回切 = env 还原 + 滚动重启, CRDB 侧 schema 保持权威副本。

**禁静默切换**: 任何方向的切换必须记录(新 ADR 或变更单), ESP ADR-24 原文沿用。
