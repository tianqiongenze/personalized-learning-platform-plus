# ADR-002: 多级缓存 L1 Caffeine + L2 Redis

**状态**: Accepted(已接线 3 服务查询路径)

## 背景

PLPP 查询热点(课程目录、知识点、租户配置等)读多写少,每次穿透到 CRDB 造成连接池压力与尾延迟。ESP 已验证"进程内 L1 + 集群 L2"两级缓存模式(参照 ESP SAD 缓存章节)。

## 决策

`platform-common` `com.platform.common.cache` 包(参照 ESP 模式落地):

- **L1**: Caffeine 进程内缓存,默认 maxSize 10_000 / expireAfterWrite 5min / expireAfterAccess 10min,按 cacheName 经 `app.cache.specs.<name>` 覆盖
- **L2**: Redis Cluster,默认 TTL 30min,key 前缀 `plp:`,null 防穿透可配
- **失效广播**: 写侧经 pub/sub 频道 `plp:cache:invalidate` 通知所有实例驱逐 L1,保证多实例最终一致
- **无 Redis 退化**: 本地开发 Redis 不可用时自动退化为纯 Caffeine,零依赖可跑
- **指标**: `app.cache.metrics=true` 时向 Micrometer 注册 Caffeine 统计(命中率视图)

接线: `MultiLevelCacheAutoConfiguration` 已注册 `AutoConfiguration.imports`;3 个服务的查询路径已用 `@Cacheable/@CacheEvict` 接入 `multiLevelCacheManager`。

## 后果

- 正面: 热点读微秒级命中 L1;跨实例一致性由失效广播保障;降级路径保证开发体验。
- 负面/约束: pub/sub 非持久化——实例重启瞬间的失效通知丢失窗口由 L1 TTL(5min)兜底;L1 命中信息需透传 `cache_hit`/`cache_layer` 元数据到响应(可观测性铁律 OSW)。
- 测试: platform-common 缓存测试用例覆盖,包含无 Redis 降级路径。

## 备选

1. **仅 Redis 单级** —— 每次读跨网络(RT ~1ms),高频读场景 L1 缺失,否决;保留为 L1 关闭时的形态。
2. **仅 Caffeine 单级** —— 多实例间数据不一致,无失效广播,否决。
3. **Spring Cache 抽象 + 其他 provider(Ehcache 等)** —— 功能等价但 ESP 已验证 Caffeine+Redis 组合,无迁移收益,否决。
